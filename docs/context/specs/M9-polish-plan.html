Carry-over 1: Mosquitto on Ubuntu 26.04

What we know: on ubuntu-latest, which is now 26.04, Mosquitto 2.1.2 in kind exits with “Unable to open config file”. That happens whether the ConfigMap is mounted as one file through subPath or as the whole directory. The same chart works locally on kind and k3d, and compose works too. The test job’s Mosquitto passes on 26.04, but it runs the image’s built-in config, so it says nothing about mounts. On ubuntu-24.04 the e2e job passes in 7 minutes.

The evidence may already exist. The failed run on d31c4bb (run 43248228548) included your see_inside, which lists the mount as the container sees it and tries to read the file. Job logs need a signed-in gh, which the sandbox can’t use, so step 2 starts with you running:

! gh run view 43248228548 --log-failed | grep -A40 -- '--- inside mosquitto'

If that doesn’t settle it, a throwaway branch, probe/ubuntu-26.04, gets a one-job workflow on ubuntu-latest. The job builds nothing, so it takes about 3 minutes. It creates kind and applies only Mosquitto and its ConfigMap, rendered from the chart with helm template --show-only. Then it prints the host’s kernel, aa-status and dmesg’s AppArmor denials, and runs three variants, each of which rules out one layer:

  • the pod with appArmorProfile: Unconfined, to test AppArmor;
  • the file through a hostPath instead of a ConfigMap, to test the kubelet’s ConfigMap volume;
  • plain docker run with a bind mount on the runner itself, to test kind.

I’ll ask before pushing the branch, and delete it afterwards. I’ll stop after two probe runs either way. There’s no deadline pressure: GitHub finishes moving ubuntu-latest by November 19, and the ubuntu-24.04 label keeps working after that.

Carry-over 2: multi-arch images on GHCR

  • Native arm64, not QEMU. Public repositories get ubuntu-26.04-arm runners for free. A release build under QEMU emulation takes many times longer than a native one, and today each image takes 2 to 4 minutes natively. The Dockerfile stays as it is, because rust:1.99.1-slim-trixie and distroless cc-debian13 already ship both architectures.
  • The image job becomes a matrix of binary × runner, using docker/setup-buildx-action, docker/metadata-action for the OCI labels, and docker/build-push-action. The org.opencontainers.image.source label links each package to the repository. On main it logs in with GITHUB_TOKEN, pushes by digest, and uploads the digest as an artifact. On a pull request it only builds.
  • A new publish job, one per binary, runs only on main and needs test, audit, e2e and image. It runs docker buildx imagetools create on the two digests with both tags, then imagetools inspect, so the log shows both platforms.
  • Permissions: the workflow keeps contents: read. Only image and publish get packages: write.
  • Who uses the images: nothing in the repo yet (decision 6). make up, make k8s and make e2e keep building from source, so they always test the code you have. The README shows how to install the cloud chart from GHCR with --set images.*.

The walkthrough

Each step is a command, what to look at, and a link to the reference section that explains it:

  1. make up, then Grafana’s Dispatch overview fills in as orders arrive.
  2. The Swagger UI and GET /plans/latest: loads, trucks, plants, ETAs.
  3. make demo: the diffs with a reason per load, as in the GIF.
  4. The Jaeger link the demo prints: one trace from the webhook to the re-dispatch.
  5. Break neckar-infra’s mapping, watch its orders land in the DLQ with ingest-cli dlq list, fix the mapping, and replay them, as the Ingest section already describes.
  6. make k8s, then kubectl get customerintegrations, pausing and resuming one.
  7. make chaos: the plant keeps batching offline, and its outbox drains once the link is back.
  8. make e2e: what CI proves on every push.

Steps

Each step ends green and becomes its own commit. Steps 2 and 3 only prove themselves in CI, so each needs a push, and I’ll ask before each one.

Step 1

Versions. Check rust-toolchain.toml, the crate versions in both workspaces, the image pins (compose, the charts, the Dockerfile, kind’s node image) and the action versions. Pull the advisory database. Bump whatever has a newer stable release, then run make test and make audit.

Step 2

Mosquitto on 26.04. Read the see_inside output you fetch, then run the probe if needed (see above). Fix the cause, unpin the e2e job, drop its ponytail: comment, and push. Done when e2e passes on ubuntu-latest. If the probe points at something we shouldn’t fix in the chart, I stop with the evidence.

Step 3

GHCR. The new image and publish jobs. Locally I can only lint the workflow, so the proof comes after the push:

  • docker buildx imagetools inspect ghcr.io/igorilic/rmc-dispatch-platform/dispatch:main lists linux/amd64 and linux/arm64, and the same goes for the other five;
  • an anonymous docker pull works. New packages may start private. If they do, you switch each one to public once in its package settings, which I can’t do from here;
  • on your Mac, the arm64 image runs natively and the amd64 image runs under emulation, and each gets as far as its first connection attempt.

Step 4

The six ADRs. Before writing each one, I read the code and the plan that made the decision, so the ADR describes what is there. One commit, docs(adr): ….

Step 5

The architecture doc. I check that every Mermaid diagram parses with @mermaid-js/mermaid-cli through npx. If the sandbox won’t run it, I check the GitHub preview after a push. I grep for every name the doc uses (crates, subjects, buckets, tables, env vars, ports), so none of them is invented.

Step 6

The demo GIF. I write docs/demo.tape. VHS needs brew install vhs, which I can’t run from the sandbox. VHS also drives a headless Chromium, which the sandbox may block. If it does, you run vhs docs/demo.tape once, and I check the GIF’s length, size and legibility.

Step 7

README and wrap-up. The new opening, the walkthrough and the GHCR section. I follow the walkthrough on a fresh stack exactly as written, and fix the README wherever reality differs. Then I tick milestone 9 in CLAUDE.md. No new variables are planned, so .env.example shouldn’t change.

Heads-up: not in M9

  • The e2e job still builds its own five images rather than reusing the image job’s. Reusing them would shorten the job, but e2e would then have to wait for the image builds and receive their images as artifacts.
  • Untagged digests from main runs that failed later stay in GHCR. A cleanup job can come once there are enough to matter.
  • The Helm charts aren’t published as OCI artifacts, and SPEC doesn’t ask for it.
  • SPEC §9’s optional Tiltfile and devcontainer don’t exist and aren’t planned.
