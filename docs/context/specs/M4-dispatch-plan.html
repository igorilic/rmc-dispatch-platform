Milestone 4 plan: dispatch v1

November 9, 2026

Milestone 4 builds the first version of the dispatch service. It keeps a Postgres copy of master data and of every order that arrives on EVENTS. On request, it plans: it splits orders into truck loads and decides which plant batches each load, when, and on which truck. It never breaks a hard constraint from SPEC §4. A REST API with OpenAPI and Swagger UI exposes orders and plans, and property tests check every hard constraint on thousands of random worlds. Improving plans with local search, re-dispatching when something changes, plan diffs and benchmarks all belong to milestone 5.

Done when:

  • make up runs dispatch. It loads master data from the seed, and its order table follows EVENTS: new, changed, and cancelled orders, with stale updates ignored.
  • POST /plans produces a plan, and GET /plans/latest shows every load and every order that couldn’t be planned, with the reason. Swagger UI runs at localhost:8081/swagger-ui.
  • Property tests check each SPEC §4 hard constraint on random worlds, and integration tests run against real Postgres and NATS containers.
  • make test, make audit and CI are green.

Where dispatch sits

Data model

How the construction heuristic plans

The plan covers orders that start within the next 48 hours. Orders are processed by requested start. Each order is split into loads: full drums, with the remainder as the last load. Then, load by load, the heuristic looks for the best slot:

  1. The target arrival is the requested start for the first load. For every later load, it is the moment the previous load finishes discharging, so the pour stays continuous.
  2. Every online plant is combined with every truck in service. The batch time is worked back from the target, using travel time and batching time.
  3. If that slot is taken, it moves later until the plant is open, a bay is free, and the truck is free. A truck is free only if it can drive empty from its previous site in time, and still reach its next trip afterwards.
  4. A slot is rejected if discharge would end after the mix design’s limit.
  5. The slot that arrives closest to the target wins, and fewer empty kilometres break ties.
  6. If no slot exists, the order is unplanned, with a reason such as “the site is 75 min from every plant, too far for the 90 min limit of C30/37-XC4”.

The random worlds cover offline plants, trucks out of service, single-bay plants, far-away sites and short mix limits. Each case also runs on the seeded Rhine-Neckar world. The soft objectives (pour gaps, lateness, empty kilometres) are measured and stored with each plan. M4 only uses them to break ties; M5’s local search optimises their weighted sum.

Order intake

A durable JetStream consumer reads events.orders.*:

  • order_upserted inserts or replaces an order;
  • order_cancelled marks it cancelled.

An event older than what is stored for that order, by occurred_at, is skipped. That is how a late, stale revision can’t overwrite a newer one. A message is acknowledged only after its transaction commits, and replays are harmless because an upsert of the same state changes nothing. Truck and ticket events stay unread until M5.

Travel time

Travel time comes from a TravelTimeProvider trait, which SPEC §3 asks for so OSRM can be plugged in later. The first implementation computes haversine distance × road factor 1.3 ÷ average speed. The speed depends on the time of day: 30 km/h in the rush hours (07–09 and 16–18 Berlin time) and 45 km/h otherwise. Address-only ship-tos use their postal code’s centroid, through the same PostalCodeGeocoder the simulators use.

Steps

Step 1

Travel time and load timing. Add the TravelTimeProvider trait, the haversine model with time-of-day speeds, and the time a load spends at the plant and on site. Tests cover rush hour against midday, and address-only sites.

Step 2

The construction heuristic, as pure code without a database. Hand-made scenarios check:

  • a continuous pour;
  • bay contention;
  • a truck reused after its return;
  • a too-far site, which ends up unplanned with its reason;
  • offline plants and out-of-service trucks being skipped.

Property tests then check each hard constraint, volume conservation and plant hours on random worlds.

Step 3

Postgres. Write the migrations and the master-data import from the seed. Plan versions are stored, and every query is checked at compile time, with .sqlx/ offline data so CI and Docker builds need no database. Integration tests run against a Postgres container.

Step 4

Order intake. A durable consumer reads events.orders.*. Integration tests use Postgres and NATS containers: a new order, a changed order, a cancellation, and a stale revision that gets ignored.

Step 5

REST API. Add the routes, the OpenAPI document and the vendored Swagger UI. Tests drive the router: POST /plans on stored orders must produce a plan that passes the same constraint checks, and the OpenAPI document must list every route.

Step 6

Compose, docs and the end-to-end check. Add a dispatch service to compose and its image to CI, write a README section “Planning”, and update .env.example. Then run make up: ingest’s orders must show up in GET /orders, and POST /plans on that live data must produce a sensible plan. Then commit.

Decisions I need from you

I’ll use the default unless you say otherwise. The first two are domain questions, where your experience matters most.

#QuestionMy default
1Which orders are planned?Every order starting within 48 h that is unconfirmed, pending or confirmed, i.e. not cancelled and not yet started. The plan is a tentative view of capacity. A dispatcher confirming orders through the API can come later.
2How is an order split into loads?Full drums, with the remainder as the last, smaller load: 42.5 m³ on 9 m³ trucks is 9 + 9 + 9 + 9 + 6.5. The alternative is equal loads (5 × 8.5).
3Does dispatch read order events already?Yes, through the stale-safe intake above. Truck and ticket events wait for M5.
4What triggers planning?POST /plans in M4. Planning automatically on events comes in M5.
5Where are trucks when planning starts?At their home plant, available from the planning time. Real positions and statuses from telematics come in M5.
6Where does a truck go after unloading?Straight to the plant of its next load. The empty kilometres are counted, and it doesn’t have to return home.
7Are plant opening hours enforced?Yes: batching only happens between opening and closing, in local time.
8How are sqlx’s compile-time checks kept working in CI?.sqlx/ is committed and regenerated with a new make sqlx-prepare, which runs against the compose Postgres.

Heads-up

  • Plan and reality diverge on purpose for now: the simulator’s trucks keep making random trips until M5 has them follow the plan.
  • Swagger UI is vendored into the binary at build time, so nothing is downloaded during a build.
  • The first plan is greedy and correct, not good. Expect some gaps and extra empty kilometres. Improving them is M5’s local search, with benchmarks at 50, 200 and 1,000 loads.
