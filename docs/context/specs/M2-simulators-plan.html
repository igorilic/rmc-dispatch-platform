Milestone 2 plan: simulators

November 9, 2026

Milestone 2 builds a fake world that behaves enough like the real one to drive every later milestone. That means 25 trucks reporting over a patchy cellular link, three batching plants issuing batch tickets, and three contractors sending orders in three very different ways. Nothing reads these signals yet; ingest arrives in milestone 3. For now, everything has to be visible in the logs and on the brokers.

Done when:

  • make up builds and starts a simulators container. make logs shows truck telematics, plant tickets, and all three customers’ orders.
  • mosquitto_sub -t 'trucks/#' -v shows live telematics, including the deliberate duplicates and reordering.
  • CSV drops from rheinbau-gmbh land on the SFTP server.
  • make test and make audit pass, CI is green, and the README explains how to watch the simulators.

Where the simulators sit

The simulated world

The world lives in one seed file, deploy/seed/rhine-neckar.json, which is compiled into the binary. It holds 3 plants, 25 trucks, 40 sites and 4 mix designs, all as the domain crate’s own types. Dispatch reuses the same file in milestone 4, so both sides agree on IDs and coordinates.

The payloads deliberately use a telematics vendor’s vocabulary (vehicle, epoch-millisecond ts_ms) rather than our domain names, so that ingest has real mapping to do. seq is a per-truck counter, so ingest can drop duplicates and restore order. All messages use QoS 1, which already allows redelivery.

One truck trip

5arrived_at_customertruckstatus → on_site

7unloadedtruckstatus → returning

The simulators only emit raw signals. Turning them into delivery events is ingest’s job in milestone 3, and tying a truck to a load is dispatch’s job, via the plan, in milestone 5. Until a plan exists, trucks pick a random site of the right customer for each trip. Travel uses the same model dispatch will use (haversine distance × road factor ÷ average speed), plus ±10 % noise, so real trips never match the plan exactly.

Three customers, three integration styles

One order generator feeds all three customers. Each one regularly creates a new order: a site from its own list, a mix, 8–150 m³ (mostly 10–60), a start time 2–26 hours ahead within plant hours, 20–60 m³/h, and a 15–30 minute maximum gap. Later ticks change the volume of an open order (15 %) or cancel one (5 %). The customers differ only in how they deliver.

bauwerk-ag: JSON webhook, full replacements

Every change is posted as the whole document again, with the same jobId and a newer updatedAt. 5 % of posts are sent twice, the way a real client does when it retries after a timeout.

rheinbau-gmbh: CSV over SFTP

Every 5 minutes, a full snapshot of all open orders is uploaded, so the same order arrives again and again. That makes idempotency matter from the very first drop. Files are written as .part and then renamed, so a reader never sees half a file. The CSV is semicolon-separated, uses decimal commas, and has German local times with no offset.

Steps

Step 1

Seed world and crate skeleton. Write the seed file and the simulators crate with env config and tracing. Tests: the seed parses into domain types, IDs are unique, every truck’s home plant exists, and every site belongs to one of the three customers.

Step 2

Truck fleet. Write the trip state machine, movement along haversine distance, and the gps/drum/status payloads. Tests use tokio’s paused clock, so no test waits in real time: a truck reaches its destination at the expected time, the statuses run in lifecycle order, and the payloads match their JSON shape.

Step 3

Flaky link. Add duplicates, reordering and dead zones. A seeded test over 10,000 messages checks that nothing is lost, that the duplicate and reorder rates stay close to their settings, that only neighbouring messages swap places, and that every dead-zone message arrives after the zone ends.

Step 4

Fake plants. Loading bays are a semaphore, and the plants issue batch tickets. Tests: with 2 bays and 5 trucks arriving together, no more than 2 batches ever run at once, and ticket numbers are unique and sequential per plant.

Step 5

Customers. Build the order generator and the three adapters: a reqwest POST or a log line for the webhooks, and a russh-sftp upload for the CSV. Tests: golden files for JSON, CSV, XML v1 and XML v2. The CSV must use decimal commas and Europe/Berlin local time. A bauwerk update must keep its jobId and move updatedAt forward.

Step 6

Image, compose and docs. One multi-stage Dockerfile: a pinned rust:1.99.1 builder and a distroless, non-root runtime. Add the simulators service, which waits for healthy infra. SFTP gets a healthcheck now that something depends on it. Add a make logs target. The README gets a “Watching the simulators” section, and new variables go into .env.example (you copy it into place, because the sandbox can’t write it). Verify with make test and make audit, plus your make up, then commit.

Decisions I need from you

The spec leaves these open. I’ll use the default unless you say otherwise.

#QuestionMy default
1What is the “fake plant”, given that SPEC §6 also has the plant-agent simulate batch tickets in M7?The fake plant is the plant’s batch computer. It publishes tickets on plants/{id}/tickets. In M7, the plant-agent reads those and forwards them with store-and-forward, instead of inventing tickets itself.
2Who decides where trucks go before dispatch exists?Trucks run autonomous trips to random sites. Telematics carry no order references; dispatch links trucks to loads through the plan. In M5 the trucks switch to following the plan.
3Should simulated time run faster than real time?No. Real time only, so timestamps stay truthful for ingest and dispatch.
4Where do webhooks go before ingest exists?Nowhere. The payload is logged until *_WEBHOOK_URL is set, which happens in M3.
5Do customers send our site IDs?Corrected after M2: yes. Orders carry our customer number and ship-to number from master data. I originally proposed customer-side references mapped by us.
6One container or one per simulator?One simulators binary and container, with each simulator running as tokio tasks.

Heads-up for later milestones

  • YAML in M3: SPEC §11 lists serde_yaml, but it is deprecated. Its fork serde_yml is flagged as unsound (RUSTSEC-2025-0068). For the mapping configs, I’ll propose serde-saphyr 2.1.1, which is maintained and was released this week.
  • Docs format in M9: SPEC §10 asks for docs/architecture.md in Markdown, which conflicts with your rule that docs are HTML. We can decide when we get there.
  • rumqttc: the spec’s MQTT client, version 0.25.1, was last released in November 2025. It is still clean in RustSec, and make audit keeps watching it.
