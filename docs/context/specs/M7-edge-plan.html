Milestone 7 plan: the edge

November 11, 2026

Today a plant is a few lines in the simulators that send batch tickets for random trips, and make demo plays the plant by hand for one load. Milestone 7 adds the plant-agent, the service that runs at the plant (SPEC §6). It pulls its plant’s slice of the plan and batches each load when its time comes. Every ticket it issues goes into a SQLite outbox first, and a forwarder sends the outbox to the cloud in order. When the link is down, the agent keeps batching from its last plan, the outbox fills up, and nothing is lost. When the link comes back, the outbox drains. Two k3d clusters, cloud and plant-walldorf, make the cut real, and make chaos shows it.

One thing to decide first. SPEC §11 names rusqlite for the outbox. Its current release can’t share a Cargo workspace with our sqlx. I checked: sqlx 0.9.0 caps libsqlite3-sys below 0.38, even though we never compile its SQLite driver. rusqlite 0.42.0 needs libsqlite3-sys 0.40.0, and only one crate in a lockfile may link sqlite3. Older rusqlite releases would fit, but they bundle a SQLite with RUSTSEC-2026-0459 (the advisory that .cargo/audit.toml already ignores, because nothing compiles it today). My default is to give the plant-agent its own small Cargo workspace (decision 1). In a scratch copy, that resolves with domain and telemetry as path dependencies and audits clean.

Done when:

  • The plant-agent pulls its plant’s slice of the plan and batches each load on time, never with more loads in parallel than the plant has loading bays, and never the same load twice, even after a restart or a plan that moved the load.
  • Every ticket goes through the SQLite outbox and reaches ingest in the order it was issued. A test cuts the broker off, queues tickets, restarts the agent, restores the broker, and checks that every ticket arrives in order and that ingest publishes each one once.
  • Offline, the agent keeps batching from its last plan, which it keeps in SQLite, and reports the plan’s age. It serves /healthz, /readyz and /status, and exports a connectivity metric and the edge sync lag.
  • make up runs an agent for Walldorf, and the Grafana dashboard gains an “Edge” row that shows data.
  • make k8s creates the pourline-net network, the local registry and both k3d clusters, deploys the cloud stack and the agent, and the agent syncs across clusters. make down removes all of it, too.
  • make chaos cuts the plant off for 120 s, then reconnects it, and prints the outbox filling and draining.
  • make test, make audit and CI are green for both workspaces, and make up is healthy.

Where the edge sits

The plant-agent

One process with three loops, which share one SQLite file:

  1. Plan sync. Every 15 s it fetches GET /plants/{id}/plan from dispatch and stores the slice, together with the time it got it. At startup it reads the stored slice, so a restarted agent that can’t reach the cloud still has a plan.
  2. Batch computer. This replaces the fake plant’s random trips with the plan’s loads. When a load’s planned batch time comes, the computer waits for a free bay (Walldorf has 2, from the seed) and then issues three tickets: batching, then loading after volume ÷ batching rate, then loaded 3 minutes later, the same timings the fake plant uses. Each ticket names the order and the load number. The computer skips loads that are already frozen, because something else batched them, and loads that a newer plan has dropped.
  3. Forwarder. It sends the oldest outbox row, waits for the broker’s PUBACK, deletes the row, and moves on to the next one. If the PUBACK doesn’t come within 10 s, the forwarder reconnects and sends the same row again.

What “no loss, no duplicates” rests on

  • Nothing is only in memory. A ticket exists only once its outbox row is committed. A row goes away only after the broker has acknowledged it. Mosquitto persists what it has acknowledged (decision 3), and ingest keeps a persistent session with manual acks, as it has since M3.
  • Order. One ticket is in flight at a time, so tickets arrive in the order they were issued. Ingest publishes them on one subject per plant, and dispatch applies them one at a time.
  • Same input, same id. A resend carries the stored bytes, including ts_ms, so ingest derives the same event id, {ticket}:{event}:{ts_ms}.
  • Duplicates across a long cut. JetStream drops a repeated id only within its 2-minute window, and the cut is 2 minutes long. A ticket whose PUBACK was lost at the moment of the cut is sent again after the window has passed. Ingest will therefore keep ticket ids in the dedup KV for DEDUP_TTL_DAYS, as it does for order ids (decision 4). There are 3 tickets per load, so the KV stays small.
  • Dispatch is idempotent anyway. A delivery is keyed by order and load number, and a repeated ticket event merges into the delivery and changes nothing.

Batching rules

  • A load is batched once its planned batch time has come. If the agent starts and finds a load more than 15 minutes overdue, which only happens after the agent itself was down, it leaves that load to dispatch and logs it (decision 9).
  • A load in batched is never batched again, even if a newer plan moves it to another time or truck. A load that was started before a restart resumes at its stage, and its remaining tickets carry the times at which they were due.
  • The fake plant in the simulators stops sending tickets for a plant that has an agent, so each plant has one batch computer (decision 8). Walldorf’s trucks still drive their random trips.

Changes in the cloud

  • Dispatch: GET /plants/{id}/plan returns the plant id, the latest version, the time it was made, and that version’s loads at the plant, each with its mix, which the ticket needs. It answers 404 for an unknown plant, and version: null with no loads before the first plan. The response type, PlantPlan, lives in domain with a wire-format test, because dispatch and the agent build in different workspaces and have to agree on the JSON. The batch-ticket payload moves from simulators::plant into domain for the same reason. Ingest keeps its own parser, so a mistake on the sending side can’t slip through unnoticed.
  • Ingest: ticket ids go into the dedup KV (see above).
  • Mosquitto: persistence true, shared by compose and k3d.

Health, status and metrics

/healthz answers once the process is up. /readyz answers once the SQLite file is open and the agent has a plan, either fetched or stored. Readiness doesn’t depend on the cloud link, because an offline plant keeps working. /status returns one JSON line that both people and make chaos can read: the link states, the outbox depth and the age of its oldest ticket, the plan version and its age, and the number of tickets queued and sent.

The agent reuses telemetry::init for console logs and the metrics listener. It creates no spans of its own (decision 11). In compose, Prometheus scrapes it with a plant label, and the dashboard’s new “Edge” row shows connectivity, outbox depth, sync lag and plan age.

Two k3d clusters

This follows SPEC §9. make k8s in this milestone does the following:

  1. It checks for k3d and kubectl and stops with the install command if one is missing. It also stops if localhost:8080 is taken, which happens when the compose stack is up.
  2. It creates pourline-net with a fixed subnet, so that make chaos can reconnect the plant node with its old IP. k3s doesn’t survive a change of node IP.
  3. It creates the registry k3d-pourline-registry:5050, builds the five images (ingest, dispatch, simulators, demo, plant-agent), and pushes them as localhost:5050/<service>:dev.
  4. It creates cloud, with its ingress on 127.0.0.1:8080, and plant-walldorf, without Traefik. Both run on a pinned k3s image. The plant cluster gets a host alias, cloud, for the cloud node’s IP on pourline-net, because pods can’t resolve other clusters’ containers by name.
  5. It applies the manifests in deploy/k3d/ with kubectl apply -k (decision 5) and waits for the rollouts. The cloud cluster runs everything from compose except Prometheus, Grafana and Jaeger (decision 6). Mosquitto’s 1883 and dispatch’s ingress reach the plant through the cloud node. The customer mappings become one ConfigMap per customer, named <customer>-mapping, which is the shape M8’s CustomerIntegration expects.

make chaos

  1. Make work for Walldorf. The demo image gets an edge mode. It runs as a one-off pod in the cloud, places three orders at the ship-tos nearest Walldorf that start as soon as possible, and waits until dispatch plans them at Walldorf. Simulated orders start 2 to 26 hours ahead, so without this step the plant would have nothing to batch during the cut.
  2. Wait until the agent has that plan, then disconnect k3d-plant-walldorf-server-0 from pourline-net.
  3. Print the agent’s status every 10 s for 120 s. The script reads it with docker exec through the plant’s own API server, which still answers while the node is cut off.
  4. Reconnect the node with the same IP, print the status every 5 s until the outbox is empty, and finish with a summary.

Steps

Each step ends green and becomes its own commit.

Step 1

The second workspace and the outbox. First, check rust-toolchain.toml, the crate versions and the image pins, and pull the advisory database. Then:

  • create crates/plant-agent as its own workspace, and add exclude to the root;
  • point build.target-dir at the root target/, so both workspaces share one build directory;
  • make make test and make audit cover both workspaces (the check that the root never compiles libsqlite3-sys stays);
  • add a MANIFEST build argument to the Dockerfile, and add the agent to the CI image matrix and to Dependabot.

Then store.rs, with only the outbox for now. Its unit tests check that rows come back in insertion order, that they survive closing and reopening the file, and that a delete removes only the acknowledged row.

Step 2

The forwarder against a real broker. This step adds MQTT QoS 1 with one ticket in flight, deletion on PUBACK, the timeout and reconnect, and the connectivity gauge. tests/forward.rs starts Mosquitto with testcontainers and checks that:

  • tickets queued while the broker is paused all arrive after it resumes, in order;
  • the same holds when the agent restarts on the same file in between;
  • a resent ticket has the same bytes as the first copy.

Step 3

The cloud side. This step adds:

  • PlantPlan and the ticket payload in domain, with wire-format tests;
  • GET /plants/{id}/plan, with API tests: one plant’s loads only, a mix on every load, 404 for an unknown plant, and an empty slice before the first plan;
  • ticket ids in ingest’s dedup KV. A test in ingest/tests/bus.rs publishes the same ticket again after its message id has left the stream’s window and expects Duplicate;
  • Mosquitto persistence.

Step 4

The agent. This step adds plan sync with the stored plan, the batch computer, the HTTP endpoints and the metrics. Unit tests, with paused time and an in-memory plan source:

  • loads start on time, never more than the bays at once, and the tickets carry the right timings;
  • a load is never batched twice: not after a newer plan moves it, and not after a restart, which resumes a load in the middle of batching;
  • frozen loads, dropped loads and loads past the grace are skipped;
  • with the plan source failing, batching continues from the stored plan, and the plan age grows;
  • /readyz waits for a plan, and doesn’t depend on the link.

Step 5

Compose and the dashboard. This step adds the agent service with a volume, AGENT_PLANTS for the simulators, the scrape target and the “Edge” row. The dashboard test can’t depend on the agent’s crate, which lives in the other workspace, so it reads the pourline_edge_ names from crates/plant-agent/src/metrics.rs. The README gets an “Edge” section. I check it on a fresh stack: tickets from the agent freeze Walldorf’s loads in dispatch, and the Edge row shows data. I also cut the agent’s container off the compose network for a minute to see the outbox drain.

Step 6

The clusters. This step adds make k8s as described above, the deploy/k3d/ manifests, and a make down that also deletes the clusters, the registry and the network if they exist. I check that every rollout is ready, that the agent in plant-walldorf has the cloud’s latest version, and that its tickets reach dispatch.

This is the riskiest step, because it depends on the Docker network, DNS across clusters and k3s’s behaviour when a node’s IP comes back. If the node doesn’t recover from a cut, I’ll stop and report what I found instead of working around it.

Step 7

make chaos, and a full run. This step adds the demo’s edge mode, deploy/k3d/chaos.sh, and the README’s k8s and chaos sections, including the prerequisite check line from SPEC §9. I run make chaos twice. In the second run, I also delete the agent’s pod during the cut, and the new pod finds its queued tickets and its plan in SQLite. After each run I check two things: that dispatch has a delivery for every load the agent started, and that ingest counted each ticket as published exactly once.

Decisions I need from you

I’ll use the default unless you say otherwise.

#QuestionMy default
1How do we get a SQLite outbox past the libsqlite3-sys clash with sqlx?The plant-agent gets its own workspace and lockfile, with rusqlite 0.42.0 and bundled, which builds SQLite 3.54.1, the patched version. It shares domain and telemetry by path, and the target/ directory. The cost is a second Cargo.lock, dependency versions repeated in the agent’s Cargo.toml, and one more line each in the Makefile, Dockerfile and Dependabot config. When sqlx allows libsqlite3-sys 0.39 or later, it merges back by deleting two lines. The alternatives are an older rusqlite in the main workspace, which would mean ignoring an advisory for code we actually compile, or a pure-Rust store such as redb, which departs from SPEC §6, §11 and §14.
2How does the plant talk to the cloud?Tickets go over MQTT on the topic the fake plant uses, and the plan comes over HTTP from dispatch. Ingest stays the only way in, with its validation, DLQ, traces and metrics, and nothing changes for the trucks. The alternative is to publish canonical events straight to JetStream, which gives a true end-to-end ack. But it would skip ingest’s checks, need NATS exposed and credentials at every plant, and still hit the 2-minute window.
3When is an outbox row done?At the broker’s PUBACK. Mosquitto gets persistence true, so a broker restart keeps what it acknowledged. The alternative is to wait until dispatch confirms the ticket, which needs a channel back to the plant and its own outbox of acks.
4How do we keep a ticket resent after a 2-minute cut from becoming a duplicate?Ingest keeps ticket ids in the dedup KV for 7 days, like order ids.
5How do the workloads get into k3d before M8’s Helm charts?Plain manifests in deploy/k3d/, applied with kubectl apply -k, which needs no extra tool. M8 turns them into charts. The alternatives are to start the Helm charts now, which is less total work but pulls part of M8 forward, or to let the compose stack act as the cloud and create only the plant cluster in M7.
6What runs in the cloud cluster?Postgres, NATS, Mosquitto, the SFTP server, ingest, dispatch and the simulators. Prometheus, Grafana and Jaeger stay in compose for now. On Kubernetes they fit better with M8’s charts, and make chaos prints the agent’s status instead.
7Should a ticket that arrives late, or contradicts the plan, trigger a re-dispatch?Not in M7. SPEC §4 lists the triggers. The next re-dispatch freezes the load where the plant actually batched it, because frozen loads come from deliveries. With the simulators’ order rate, that happens within a few minutes. The alternative is a new trigger, load_batched_off_plan, so the plan corrects itself right after the drain.
8A plant with an agent would also have the fake plant sending tickets. What should happen?The fake plant goes quiet for plants in AGENT_PLANTS, so each plant has one batch computer, and its bays aren’t used twice.
9What happens to a load that is already overdue when the agent starts?If it is up to 15 minutes late, the agent batches it. If it is later than that, the agent leaves it to dispatch and logs it. This only matters after the agent itself was down. While the link is down, the agent batches on time.
10What does “how stale its plan is” measure?The time since the agent last heard from dispatch. A plan that hasn’t changed for an hour isn’t stale if dispatch confirmed it 10 s ago.
11Should the agent trace its tickets?No. MQTT 3.1.1 has no headers to carry a traceparent, and in k3d the plant can’t reach Jaeger anyway. Ingest’s mqtt message span still starts each ticket’s trace, as it does today.

Heads-up: not in M7

  • Dispatch doesn’t know that a plant is cut off. If a re-dispatch runs during the cut, for example for a new order, it can move Walldorf’s overdue loads, even though Walldorf batches them from its last plan. After the drain, the next re-dispatch freezes them where Walldorf batched them (decision 7). If the cloud moved such a load to another plant, it could be batched twice. That can’t happen here yet, because the simulated plants don’t batch planned loads.
  • Only Walldorf has an agent. Mannheim and Weinheim stay simulated. Another agent means one more cluster and one more kustomization.
  • The plant and the cloud don’t authenticate each other: MQTT is anonymous and HTTP is plain, as in the rest of the dev stack.
  • make k8s doesn’t install Helm charts, the operator or CustomerIntegrations yet. Those come in M8, and so does the end-to-end test in CI (kind, SPEC §12). CI in M7 builds and tests the agent, but doesn’t run k3d.
  • make up and make k8s are alternatives. Both use localhost:8080, and together they need more than SPEC’s 8 GB. The first make k8s builds five release images, which takes a while.
  • Simulated trucks still drive random trips and don’t follow the plan, as since M2.
