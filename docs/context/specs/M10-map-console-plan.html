Plan: milestone 10, the map console

November 14, 2026

Today you watch Pourline through logs, Swagger, Grafana in compose, and make chaos’s status lines. Nothing shows the world itself: where the trucks are, what they’re doing, and how the plan moves when something breaks.

Milestone 10 adds a map console to the local k8s stack, at http://localhost:8080/console in the cloud cluster. It shows the plants, sites and trucks on a map with a status legend. From it you can break a truck down, delay a site, take a plant offline, re-plan, push a sync to the Walldorf plant, and run Make chaos, which cuts that plant’s uplink as make chaos does.

Its updates travel the real path: MQTT → ingest → NATS → console → browser. Each action is traced in Jaeger, and the console has a row in Grafana, which now runs in k8s with Prometheus. The page takes the look of your Spotlight design system.

This replaces the first draft, which ran the console on the host with the Docker socket. It follows your answers: sync for the plant action, the console inside local k8s, the Spotlight look, updates through the whole stack with Grafana and Jaeger, chaos in k8s, and milestone 10. Five independent reviews checked it against the code, and their fixes are in.

The console’s state

  • One state per console, never one per page. Master data comes from the seed compiled into every binary: names, customers, sites with the postal-code geocoder, capacities and bays. So the first paint never waits for dispatch.
  • At startup the console subscribes before it reads anything.
    • It subscribes to plans.updated, and opens an ordered consumer on the EVENTS stream for events.trucks.> and events.plants.> that starts at each subject’s last message.
    • Then it reads the new GET /world: truck status and position with their report times, plant status and the latest plan version. It also reads the latest diff.
    • Every truck field keeps its newest value by time, whichever source it came from, so a lagging /world can’t undo a newer event. Starting at the last message gives each truck and plant its latest event at once. It also avoids an async-nats quirk that replays the whole 7-day stream after an early reconnect.
  • It reads /world again after each plans.updated and after a NATS reconnect. A newer plan version there catches an announcement that core NATS dropped. For each new version it fetches the diff once and pushes it once.
  • A connecting page gets retry:, then a copy of the state taken under the same lock as the broadcast, then the live events. A heartbeat carries the world time every 15 s. A page that falls behind is dropped; its browser reconnects and gets a new copy. Only popups make a page call dispatch.
  • The page keeps the newest value per truck field and ignores plan versions that aren’t newer than its own. An error response, such as a 502 or 503 during a rollout, ends an EventSource for good, so the page creates a new one after a random 1–5 s. It does the same after 45 s without a heartbeat. It closes the stream while the tab is hidden, so idle tabs don’t hold the browser’s six connections to localhost:8080.
  • Ages and fading use the world time from the heartbeat, not the browser’s clock. That way a shifted world fades correctly.

Traces

  • Each action starts a root span in the console, and the response returns its trace_id for the log.
  • telemetry gains two string helpers, with no new crate: one returns the current span’s traceparent, and one continues a span from such a string. They carry the trace in an HTTP header and in the sync command’s payload.
  • Dispatch opens a request span only for a request that has a valid traceparent and no X-Forwarded-For, that is, one that didn’t come through Traefik. That covers cloud pods, the plant through the uplink, compose’s loopback port and port-forwards. Its handlers then join the caller’s trace. Every other request passes through untouched: probes and polls add no traces, and requests through the ingress start their own traces, as today (decision F).
  • Dispatch publishes plans.updated with the re-dispatch’s traceparent, and the console’s push continues that trace. So each Changes entry links its trace; for a breakdown, that is the trace ingest started.
  • The plant-agent opens a span for a commanded sync. The span continues the command’s traceparent, and the agent sends the span’s own on that fetch. Its spans reach Jaeger through the uplink, so a cut drops them too. Periodic polls open no span.
  • GPS and drum events stay out of Jaeger, as today: ingest samples them out, and the console follows that decision.

Metrics and dashboards

  • The console exports:
    • pourline_console_clients
    • pourline_console_pushed_total{kind}
    • pourline_console_actions_total{action,outcome}
    • pourline_console_event_lag_seconds{kind}: the time from ingest receiving a truck or ticket event to the push, on the world clock. The replay at startup is left out.
  • They go in a collapsed “Console (k8s)” row, so compose’s Grafana isn’t cluttered. The dashboard test reads their names from console::metrics::NAMES, as it does for ingest.
  • Prometheus in k8s finds pods in its namespace through a namespaced Role:
    • containers with a port named metrics (ingest, dispatch, console);
    • the operator’s ingest-<name> pods, through one relabel to :9464, so the operator doesn’t change. The SFTP CronJob’s pods live seconds, so they mostly go unscraped, as before.
    The plant is a static target with the plant=plant-walldorf label that the Edge row needs.

Make chaos, from the console

The console runs make chaos’s steps inside the cluster, and the edge card shows each one:

  1. It places three orders at the ship-tos nearest Walldorf, through the bauwerk-ag and neckar-infra webhooks, as demo edge does. That code moves from the demo binary into the simulators library, so both use the same orders.
  2. It waits until a plan version plans them and Walldorf’s agent holds that version.
  3. It disables the uplink’s proxies for CHAOS_SECONDS (120). Toxiproxy closes both sides of every connection and refuses new ones. Reconnect ends the cut early.
  4. After the reconnect it waits up to 120 s for the outbox to drain, and reports as chaos.sh does: “3 tickets waited out the cut, sent in order within 9 s”, or “No ticket fell due; run it again”.

Only one run happens at a time, and its state lives in the console. The uplink’s real state comes from Toxiproxy every 2 s. At startup the console resets the uplink, retrying until Toxiproxy answers, so a console that died mid-cut can’t leave the plant cut. make chaos stays the hard cut, the plant node off the network, and now starts by ending a console run, best effort.

What changes where

  • telemetry: the two string helpers.
  • dispatch:
    • GET /world: a new store query for the report times, which are stored but unread today, and the latest plan version. Master data stays in the seed.
    • plans.updated, carrying the version and its time, with the traceparent in its headers. The worker publishes it right after save_plan; a failed publish is logged, never returned. The worker takes an optional NATS client, so the API tests stay NATS-free.
    • The request-span middleware.
    • The OpenAPI route-list test gains /world.
  • domain: the plans.updated subject and message, the sync topic, and the breakdown topic. The simulators, the demo and the console share one copy instead of three.
  • simulators: demo edge’s order selection moves into the library.
  • plant-agent:
    • It subscribes to its sync topic after every ConnAck.
    • The forwarder’s driver task sees every packet and hands a command to the sync loop through a watch channel, so a command that arrives while a ticket waits for its PUBACK isn’t lost.
    • A commanded sync opens a span and passes the traceparent on if it is valid; a malformed one is ignored.
    • No persistent session, and no extra resync on reconnect.
  • console, a new crate (library plus binary) built by the same Dockerfile:
    • It uses [lints] workspace = true, thiserror in the library and anyhow in main.
    • axum, async-nats, rumqttc, reqwest and futures, all already workspace dependencies.
    • It reads dispatch’s JSON without types, so it doesn’t depend on dispatch.
    • The page is one HTML, one CSS and one JS file, embedded, with Leaflet 1.9.4 pinned with SRI (2.0 is still in beta), and no build step.
    • Markers glide between fixes with a requestAnimationFrame tween, because a CSS transition fights Leaflet’s zoom.
  • pourline chart:
    • The console’s Deployment (one replica, Recreate, probes on /healthz, a metrics port) and Service.
    • The Ingress paths /console, /grafana and /jaeger. Traefik ranks longer paths first and strips nothing, so each backend serves under its own prefix.
    • Prometheus (Role, scrape config) and Grafana, which loads its files from the chart, takes its root URL from a publicUrl value, and gets its two compose links rewritten to absolute k8s URLs with replace.
    • Jaeger’s base path, --set=extensions.jaeger_query.base_path=/jaeger.
    • The uplink, rendered only when edge.plantAddress is set:
      • Toxiproxy ghcr.io/shopify/toxiproxy:2.13.0, with its three proxies in a ConfigMap (-host=0.0.0.0 -config=…).
      • A readiness probe on its API, GET /proxies/dispatch, which still answers during a cut, and no liveness probe.
      • Its API on a ClusterIP Service, and its proxies on a LoadBalancer.
    • Checksum annotations, so a config change rolls Prometheus, Grafana and Toxiproxy.
    • Mosquitto goes back to ClusterIP, because nothing outside the cluster uses cloud:1883 any more. mosquitto.serviceType and its e2e override go.
  • plant-agent chart: dispatchUrl: http://cloud:8088, mqttUrl: mqtt://cloud:1884, and an OTLP endpoint at http://cloud:4318. Its Service becomes a LoadBalancer on the plant node, and keeps its name and port names, so chaos.sh’s status read still works.
  • Scripts: k8s.sh builds the console image and passes the plant node’s IP as edge.plantAddress. chaos.sh first ends a console run.
  • Grafana’s files move to deploy/helm/pourline/files/grafana/ (decision C). Compose mounts them from there, and the dashboard test’s path follows.
  • CI and e2e: the console joins the image and publish lists. The e2e installs it without a plant, so with no uplink and no edge card. It asserts that Prometheus has ingest, dispatch, the console and ingest-bauwerk-ag up, and reads /console/api/snapshot through the API server proxy.

Security

  • The console is reachable only through 127.0.0.1:8080, all that k3d publishes. Nothing gets the Docker socket. Toxiproxy’s API has only a ClusterIP Service, and it refuses browser user agents anyway.
  • Every POST, PUT and DELETE needs an X-Pourline-Console header and a Host from PUBLIC_URL: localhost:8080, or 127.0.0.1:8080 with it. The header stops other sites, which can’t send it without a CORS preflight the console never answers. The Host check stops DNS rebinding.
  • GETs aren’t guarded. They serve only simulated data, and that lets the e2e read the snapshot through the API server proxy. /healthz sits at the root, outside /console, for the probes.
  • Truck, site and plant ids must exist in the seed before they reach an MQTT topic or a dispatch URL. Commands are published with QoS 1 and never retained, because a retained breakdown would break the truck again on every reconnect.

Heads-up

  • The simulated plants ignore plant status. After Take offline the plan moves away from the plant, but simulated trucks still load there.
  • Stadia’s keyless tiles work only from localhost or 127.0.0.1, and the browser needs internet access for them. If tiles fail, the map says so instead of going blank.
  • When the worker merges two triggers into one run, the run joins the first trigger’s trace and only links to the second.
  • A plant toggled elsewhere, for example in Swagger, with an empty diff shows on the console after the next plan update or reconnect.
  • The cloud cluster gains four pods: the console, the uplink, Prometheus and Grafana. README’s 4 CPUs and 8 GB should hold; I check in steps 3 and 4.
