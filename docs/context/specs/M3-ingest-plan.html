Milestone 3 plan: ingest

November 9, 2026

Milestone 3 turns everything the simulators send into canonical events on NATS JetStream. That covers orders from three customers with three different formats, plus truck telematics and batch tickets. Customer formats are described in YAML, so there is no customer-specific Rust. Duplicates never create duplicate orders. Anything that can’t be mapped lands in a dead-letter stream, and ingest-cli can replay it after the mapping is fixed. Everything follows the master-data model from the M2 correction: orders carry our customer and ship-to numbers, and ingest checks both.

Done when:

  • make up runs ingest. The simulators post to it, and the EVENTS stream grows while DLQ stays empty in normal operation.
  • Bauwerk retries, repeated rheinbau snapshots and duplicated telematics produce no duplicate events.
  • ingest-cli validate names the exact row, field and reason for every problem in a broken sample.
  • Breaking a mapping fills the DLQ. After the mapping is fixed, ingest-cli dlq replay empties it into EVENTS.
  • make test passes, including the new integration tests against a real NATS container, and so do make audit and CI.

Mapping configs: customers in YAML, not Rust

Each customer integration has customers/<name>/mapping.yaml. It declares the format, where each canonical field comes from, how to convert it, which customer number the integration may order for, and how to build the idempotency key. Here is rheinbau-gmbh in full:

# Orders must be for this master-data customer.
customer: "10001002"
format: csv
csv: { delimiter: ";", header: true }
timezone: Europe/Berlin
fields:
  order_ref:       { column: Auftragsnr }
  customer:        { column: Kundennr }
  ship_to:         { column: Warenempfänger }
  mix:             { column: Sorte }
  volume_m3:       { column: Menge, number: decimal_comma }
  requested_start: { column: Liefertermin,
                     datetime: "%d.%m.%Y %H:%M" }
  pour_rate_m3_per_h:
                   { column: Leistung, number: decimal_comma }
  max_gap_minutes: { column: MaxPause, number: integer }
  status:
    column: Status
    map: { bestätigt: pending, storniert: cancelled }
# Snapshots carry no revision, so hash the mapped content.
idempotency: { content_hash: true }

Validation runs after mapping and checks each order against master data:

  • the customer number is the integration’s own customer;
  • the ship-to exists and belongs to that customer;
  • the mix exists;
  • volume, pour rate and gap are positive.

XML is parsed without entity expansion (quick-xml doesn’t do it), so no XXE.

Canonical events

Telematics stay facts about trucks. Turning them into delivery events needs the plan, which tells us which load a truck carries, so that is dispatch’s job in M5. Events keep occurred_at from the source, so consumers can tolerate disorder.

Idempotency

Ordering: to keep it safe, a message is published with the key as its JetStream message id first, and only then is the key recorded in the KV. A crash between the two is covered by JetStream’s 2-minute duplicate window. Telematics duplicates arrive within seconds, so the message id alone is enough for them, and they need no KV.

Dead letters and replay

Transient failures, where NATS is slow or down, are not poison. They retry with exponential backoff (0.1 s doubling to 3.2 s, 6 attempts), and if NATS still isn’t back, the sender is told to try again. Only messages that can never succeed as they are go to the DLQ.

Backpressure: slow downstream, nothing lost

ChannelWhen NATS is slow or downWhy nothing is lost
WebhooksAt most MAX_IN_FLIGHT requests are processed at once. Beyond that, ingest answers 503 with Retry-After.202 is only sent after the event is in JetStream. The simulators retry and honour Retry-After.
MQTTA bounded channel fills up, so ingest stops polling and TCP pushes back to the broker.QoS 1, a persistent session and manual acks: a message is acked only after its event is in JetStream. Mosquitto’s queue limit is raised.
SFTPThe current file waits.A file moves to processed/ only after its last row is handled. A crash means reprocessing, and dedup absorbs the repeats.

Steps

Step 1

Shared master data and canonical events. Move the seed loader into domain, so the simulators, ingest and later dispatch read the same master data, and add the event envelope with wire-format tests. Three simulator fixes:

  • orders whose start has passed leave the customers’ books, so CSV snapshots stay bounded;
  • webhook posts carry a token;
  • the simulators honour 503/Retry-After with more retries.

Step 2

Mapping engine and the three mapping.yaml files. This covers the parsers, transforms, version selection, validation against master data and idempotency keys. Tests:

  • every good sample maps to golden canonical events;
  • every broken sample produces its exact error list;
  • a property test checks that the same content always gives the same key and any changed field gives a different one.

Step 3

ingest-cli validate. It prints the report from Step 2 and exits non-zero when anything is invalid. Tests pin the output for the broken samples.

Step 4

NATS pipeline. Ingest creates the EVENTS and DLQ streams and the dedup KV at startup, and the step adds publishing with retries and dead-lettering. Integration tests run against a NATS container started by testcontainers:

  • delivering the same order twice yields one event;
  • a changed order yields a second event;
  • a poison message lands in the DLQ with its errors.

Step 5

Sources.

  • Webhooks get token auth, a 1 MiB body limit and 503 when full.
  • The MQTT subscriber uses manual acks and a persistent session, and maps telematics and tickets.
  • The SFTP poller moves files to processed/ when they are done.

Tests: a webhook test checks that a request beyond capacity gets 503 and that a 202 means published. Unit tests cover telematics mapping.

Step 6

ingest-cli dlq list and replay. An integration test breaks a mapping, sends a message, fixes the mapping, replays, and then checks that EVENTS has one more event and the DLQ is empty.

Step 7

Compose, docs and the end-to-end check. Add an ingest service, point the simulators at the webhooks, and raise Mosquitto’s queue limit. The README gets a “Watching ingest” section, CI builds the new images, and .env.example gets the new variables. Then check stream counts on localhost:8222/jsz while the stack runs, and commit.

#QuestionMy default
1Which order events does ingest emit? (SPEC §4 lists NewOrder, OrderVolumeChanged and OrderCancelled as re-dispatch triggers.)order_upserted, carrying the full order, and order_cancelled. Ingest stays almost stateless, and dispatch derives new and changed orders by comparing with what it has stored (M4–M5).
2Which status does an order from a customer system get?pending, following your definitions: the customer has confirmed and the dispatch centre hasn’t yet.
3What is our order id?<customer number>/<customer’s order no>, e.g. 10001002/RB-7781.
4Do plant tickets go through ingest?Yes, until M7, when the plant-agent takes them over with store-and-forward.
5Should telematics be mapped in YAML too?No. There is one telematics vendor with a fixed format, so a small Rust mapper is enough. YAML is for customer integrations, where formats vary.
6Where do idempotency keys live?Order keys go in a NATS KV bucket with a 7-day TTL, since snapshots repeat for days. Telematics rely on JetStream’s 2-minute message-id window.
7Should webhooks be authenticated? (The spec doesn’t say; M8’s CRD has Secret refs.)Yes: one bearer token per integration, compared in constant time. Dev tokens are throwaway values in .env.example.
8Which YAML library?serde-saphyr. SPEC §11’s serde_yaml is deprecated, and its fork serde_yml is flagged as unsound (RUSTSEC-2025-0068).
9Where does master data come from until Postgres (M4)?The seed file, through a shared loader in domain.

Heads-up

  • make test now needs Docker, because SPEC §12 wants integration tests with testcontainers. On colima, the Makefile takes DOCKER_HOST from your Docker context, and CI runners already have Docker.
  • Stale revisions: ingest skips duplicates but doesn’t reorder revisions that arrive out of order. order_upserted carries the source’s revision or timestamp, so dispatch can ignore an older one (M4).
  • No healthcheck for ingest in compose: the distroless image has no curl. /healthz exists, and compose waits for “running”. M6 brings proper probes.
