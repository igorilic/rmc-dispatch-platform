Milestone 8 plan: the operator

November 11, 2026

Today one ingest process serves every customer. It reads every mapping once at startup, and in k3d it runs from M7’s plain manifests. Milestone 8 makes each customer integration a Kubernetes object. A CustomerIntegration names its channel, its mapping ConfigMap and its credentials Secret, and the new operator (kube-rs) runs it as its own workload (SPEC §7). Before a mapping reaches a pod, the operator checks it with ingest’s own parser. It also pauses and resumes the integration, cleans up with a finalizer when the resource is deleted, and keeps the resource’s status up to date: its phase, its last successful ingest and its dead letters. M7’s manifests become two Helm charts. CI gains an end-to-end test: a kind cluster, a Helm install, the demo scenario, and checks that a plan exists and the DLQ is empty (SPEC §12).

One thing to decide first. In SPEC §7, the operator reconciles “the matching Deployment/CronJob” for each integration, with that integration’s own replicas, schedule and pause switch. None of that can apply to a single customer while one process serves them all. My default is to run each integration as its own workload from the same ingest image (decision 1). A webhook integration becomes a Deployment behind its own path. An SFTP integration becomes a CronJob that polls once per run. For that, ingest gets a mode switch, and in Kubernetes the chart’s own ingest Deployment keeps only MQTT. Compose stays as it is: there, one ingest process still runs everything.

Done when:

  • A webhook CustomerIntegration runs as a Deployment with spec.replicas pods, a Service and the ingress path /webhooks/<name>. An SFTP one runs as a CronJob on spec.schedule. Each runs the ingest image with only its own mapping and credentials.
  • The operator checks the mapping and the credentials before it rolls them out. A broken mapping sets the phase to Failed with the parser’s message, and it never reaches a pod. A valid change to the mapping or the credentials rolls the workload.
  • paused: true scales a webhook integration to 0 or suspends an SFTP integration’s CronJob, and the phase becomes Paused. paused: false resumes it.
  • When a CustomerIntegration is deleted, its workload stops before the resource disappears (finalizer).
  • The status (phase, message, last successful ingest, dead letters) is at most 30 s old, and kubectl get customerintegrations shows it in columns.
  • make k8s installs the two charts and applies the three example CustomerIntegrations, which all reach Running. make chaos still works.
  • make e2e and CI’s new e2e job pass: the demo scenario runs on kind, rheinbau’s CronJob ingests a drop, and the DLQ stays empty.
  • make test, make audit and CI are green, and make up is healthy.

How a CustomerIntegration runs

The resource

This is SPEC §7’s resource with one new field, credentialsSecret (decision 2), and a message in the status:

apiVersion: pourline.dev/v1alpha1
kind: CustomerIntegration
metadata:
  name: rheinbau-gmbh                # the integration, as in customers/rheinbau-gmbh/
spec:
  channel: sftp                      # sftp | webhook; must match the mapping's channel
  mappingConfigMap: rheinbau-gmbh-mapping
  credentialsSecret: rheinbau-gmbh-credentials   # sftp: username, password; webhook: token
  schedule: "*/5 * * * *"            # sftp only, and required for it
  replicas: 1                        # default 1; sftp allows only 1
  paused: false
status:
  phase: Running                     # Pending | Running | Paused | Failed
  message: null                      # why, whenever it isn't Running
  lastSuccessfulIngest: "2026-11-11T14:05:12Z"
  deadLetterCount: 0

The Rust types generate the CRD. Its CEL rules reject a missing schedule on SFTP, a schedule on a webhook, and more than one SFTP replica, so kubectl apply refuses these before anything runs. The generated YAML is committed in the chart, and a test fails if it drifts from the types.

Before a rollout

The operator rolls out a mapping only if all of these hold:

  • the ConfigMap exists and has a mapping.yaml key;
  • ingest’s Mapping::parse accepts it, which is the same check ingest-cli validate starts with, and the mapping’s channel matches spec.channel;
  • the Secret exists and has the keys its channel needs.

If one of them fails, the phase becomes Failed, and the message says which check failed and why. The workload is left alone and keeps running on its last valid mapping (decision 3). Once the ConfigMap or Secret is fixed, the operator notices the change and rolls it out.

Pause, resume, delete

  • Pause sets a webhook integration’s replicas to 0, so its requests fail until it resumes. It suspends an SFTP integration’s CronJob, so files wait on the server. Resume undoes both. Nothing is lost either way: customers retry, the files stay where they are, and dedup absorbs any repeats.
  • Delete goes through the finalizer (decision 5). The operator first deletes the workload in the foreground and waits until it is gone. Then it removes the integration’s entry from the ingest-status KV, which is the one thing outside Kubernetes. That step is best effort: if NATS is down, it logs a warning and the deletion continues. Only then does it release the resource. Dead letters stay in the DLQ, so a re-created integration can still replay them.

Status

PhaseWhen
PendingThe workload is applied but not ready yet: the webhook Deployment has fewer ready replicas than requested.
RunningWebhook: every replica is ready. SFTP: the CronJob exists and its last run didn’t fail.
Pausedspec.paused is true.
FailedThe mapping or the credentials are missing or invalid, the API server refused the workload, or the last SFTP run failed. message says which.

deadLetterCount is the number of messages on the DLQ subject dlq.<name>. lastSuccessfulIngest is the time of the integration’s last delivery (a webhook request or an SFTP file) in which at least one record was published or recognised as a duplicate (decision 4). A delivery whose records were all dead-lettered doesn’t count, and neither does a poll that found no files. Neither value causes a Kubernetes event, so the operator re-reads both every 30 s.

  • The ingest-status KV: Bus::deliver writes the integration’s last successful ingest after each delivery that counts (see above). Bus::connect creates the bucket next to the dedup bucket.
  • A read-only status reader in ingest::nats gives the dead-letter count and the last ingest for one integration, and deletes the KV entry when an integration is deleted. Unlike Bus::connect, it never creates or reconfigures a stream or bucket, so the operator can’t change the dedup TTL by accident.
  • The demo reads BAUWERK_WEBHOOK_URL and NECKAR_WEBHOOK_URL, the variables the simulators already use, instead of INGEST_URL. In Kubernetes, each webhook integration has its own Service, so a single base URL no longer reaches both. Compose sets both variables.

Onboarding a customer means adding these three objects; the chart doesn’t change (decision 6).

The operator gets the ingest image from the chart, so integrations always run the same build as the core ingest. A new ingest image restarts the operator, which re-applies every workload with that image. The chart also passes the operator NATS_URL, the SFTP host and port, and the OTLP endpoint, and the operator hands them on to the workloads. mosquitto.conf moves into the chart, and compose mounts it from there, so only one copy exists.

make k8s keeps the network, the registry and the clusters from M7. What changes:

  1. It also checks for helm, and builds and pushes a sixth image, operator.
  2. It applies the CRD with kubectl apply --server-side first, because Helm never upgrades what is in crds/ (decision 7). Then it runs helm upgrade --install for each chart, with every image pinned to the digest it just pushed, as M7 does with sed today.
  3. It applies deploy/integrations/ and waits until all three integrations are Running.
  4. Clusters left from M7 hold objects that Helm didn’t create, and Helm won’t adopt them. make k8s detects this and stops, with a hint to run make down once first.

deploy/k3d/cloud/ and deploy/k3d/plant-walldorf/ are removed. chaos.sh only changes the demo’s webhook URLs.

The end-to-end test

CI runs make e2e in a new job, and you can run the same command locally. It runs deploy/e2e/run.sh, which:

  1. creates a kind cluster, pourline-e2e, from a pinned node image, and writes its kubeconfig under target/, so ~/.kube/config is never touched;
  2. lints both charts, builds the images for ingest, dispatch, the simulators, the demo and the operator, and loads them into kind;
  3. applies the CRD, installs the cloud chart with deploy/e2e/values.yaml (local images, rheinbau drops every 30 s, a slow random-order rate as in make demo), applies deploy/integrations/, and patches rheinbau’s schedule to every minute, which also tests a spec change;
  4. waits until all three integrations are Running;
  5. runs the demo scenario as a pod. It already fails if an order isn’t planned, a frozen load moves or a diff is missing;
  6. waits until rheinbau’s lastSuccessfulIngest is set, which proves the CronJob path;
  7. checks that /plans/latest has loads, that the DLQ stream holds 0 messages (both read through the API server’s service proxy, as make chaos does), and that every integration reports 0 dead letters;
  8. on failure, prints the integrations, pods, events and the logs of the operator, ingest and dispatch. Locally, it deletes the cluster unless E2E_KEEP=1 is set.

The plant chart isn’t part of it. One kind cluster tests the cloud, and make k8s keeps covering the plant.

Steps

Each step ends green and becomes its own commit.

Step 1

Ingest, one part at a time. First, check rust-toolchain.toml, the crate versions, the image pins and the action versions, and pull the advisory database. Then:

  • INGEST_MODE, with config tests;
  • the ingest-status KV and the status reader. Tests in ingest/tests/bus.rs check that a delivery with a published record or a duplicate sets the time, that one whose records were all dead-lettered doesn’t, that the counts are per integration, and that the reader doesn’t create anything on a fresh server;
  • the demo’s webhook URLs. make up and make demo still pass.

Step 2

The resource and what it becomes. This step adds crates/operator with the CRD types, operator crd, the generated CRD in the chart’s crds/ and the drift test, plus the pure functions that build the desired objects and the phase. Unit tests check that:

  • a webhook integration becomes a Deployment, Service and Ingress with the right replicas, 0 when paused, INGEST_MODE=webhooks, the mapping mounted where MAPPINGS_DIR expects it, the token from secretKeyRef, and owner references;
  • an SFTP integration becomes a CronJob with its schedule, suspend when paused, concurrencyPolicy: Forbid and INGEST_MODE=sftp-once;
  • the pod template’s hash changes when the mapping or the Secret’s version changes, and only then;
  • each check before a rollout fails with its own message, including a channel that doesn’t match the mapping’s;
  • the phase follows the table above;
  • the CRD carries the CEL rules and the printer columns.

Step 3

The controller. This step adds the reconciler with server-side apply, the watches on ConfigMaps and Secrets, the status refresh and the finalizer. tests/reconcile.rs starts k3s and NATS with testcontainers (the same rancher/k3s image k3d uses) and runs the controller against them. The pods won’t start, because k3s doesn’t have the image, so these tests check objects and status, and the e2e test checks Running. They check that:

  • applying an integration creates its objects, and the status reports dead letters seeded into the DLQ;
  • pausing and resuming change replicas and suspend, and the phase;
  • a missing ConfigMap gives Failed, and creating it recovers without touching the integration;
  • a broken mapping edit leaves the operator’s copy and the Deployment unchanged;
  • deleting the integration removes its objects and its KV entry, and then the resource itself.

k3s needs a privileged container. k3d works here, so k3s should too. If it doesn’t, I’ll stop and report what I found.

Step 4

Charts and make k8s. This step adds both charts, deploy/integrations/, the new k8s.sh, the move of mosquitto.conf, the change to chaos.sh, and the operator in the CI image matrix. The old kustomizations are removed. I check it on fresh clusters (make down && make k8s):

  • all three integrations are Running, and orders from all three customers reach dispatch;
  • a webhook gets through the ingress at localhost:8080/webhooks/bauwerk-ag;
  • a broken mapping edit gives Failed and the pods stay up; the fix rolls them;
  • pausing, resuming, deleting and re-applying an integration each work;
  • make chaos still passes.

The README gets an Operator section, and its Kubernetes section changes to describe the charts.

Step 5

The end-to-end test. This step adds deploy/e2e/, make e2e and the CI job. Running it here needs kind, which isn’t installed and which I can’t install from the sandbox: brew install kind. Running it in CI needs a push, and I’ll ask before I push.

Step 6

Wrap-up. This step adds Helm and kind to the README’s prerequisites and its check line (SPEC §9), gives you the .env.example lines, and ticks the milestone in CLAUDE.md.

Decisions I need from you

I’ll use the default unless you say otherwise.

#QuestionMy default
1How does a CustomerIntegration map onto workloads?Each integration gets its own workload from the ingest image: a Deployment, Service and Ingress path for a webhook, and a CronJob running sftp-once for SFTP. In Kubernetes the core ingest keeps only MQTT. Compose doesn’t change. The alternative is for the operator to manage only the configuration of the one shared ingest and restart it on each change. That is less code, but it ignores replicas, schedule and pause per integration, and it isn’t SPEC §7’s Deployment/CronJob.
2SPEC §7 has the operator reconcile “Secret refs”, but its example has no field for them. Where do credentials go?A required field, credentialsSecret, which needs token for a webhook, or username and password for SFTP. Pods get the values through secretKeyRef. The operator reads the Secret only to check its keys, and puts the Secret’s resourceVersion into the pod template, so a rotation rolls the pods without a hash of the password appearing anywhere. The alternative is to keep the shared credentials from M7, so integrations have no Secret of their own.
3What happens to a broken mapping?The operator checks it and copies only valid mappings into its own ConfigMap, which the workload mounts. A broken edit sets Failed and never reaches a pod, not even one that restarts. The alternative is to mount your ConfigMap directly and only report the problem. That is simpler, but the next CronJob run, or any webhook pod that restarts, would load the broken mapping.
4Where does lastSuccessfulIngest come from?Ingest writes it to a new KV bucket, ingest-status, after each delivery in which a record was published or was a duplicate. The alternatives need no change to ingest: the time of the last event on events.orders.<customer> (but rheinbau’s snapshots are mostly duplicates, so a healthy integration would look stale), or the CronJob’s lastSuccessfulTime (which exists only for SFTP).
5What does the finalizer do?It stops the workload first, then removes the integration’s ingest-status entry on a best-effort basis, so it never blocks on NATS. Owner references delete the objects anyway. Dead letters are kept. The alternatives are to purge the integration’s dead letters too, which destroys data that could still be replayed, or to block deletion while dead letters remain.
6How are the charts split, and where do the example integrations live?Two charts, pourline for the cloud and plant-agent for the plant. The infrastructure goes in as plain templates with our pinned images, not as subcharts. The customers’ ConfigMaps, Secrets and CustomerIntegrations live in a kustomization outside the charts, because Helm can’t read customers/, and because onboarding a customer shouldn’t need a chart release. The alternative is to put them in the chart’s values, with copies of the mappings.
7How is the CRD installed and upgraded?It is generated from the Rust types, committed in the chart’s crds/ directory, and kept in sync by a test. make k8s and make e2e apply it server-side before helm upgrade, because Helm installs crds/ once and never upgrades it. The alternative is to template the CRD, so Helm upgrades it, but helm uninstall would then delete every CustomerIntegration.
8How much can the operator touch, and how many copies of it run?Its own namespace only, through a Role rather than a ClusterRole. It runs as one replica with the Recreate strategy and without leader election, so two operators never reconcile at the same time. The alternative is to run cluster-wide with leader election, which is more RBAC and more code for one namespace.
9What does the e2e test run on, and which scenario does it use?kind, as SPEC §12 says. make e2e runs the same script locally (brew install kind). The scenario is the existing demo, which already checks its own results, plus rheinbau’s CronJob and the checks on the DLQ. The alternative is k3d in CI too, so there is only one tool, but that departs from SPEC §12.
10Should Prometheus and Grafana move into the cloud chart? (M7 deferred them to M8.)Not in M8. They stay in compose, and kubectl get customerintegrations becomes Kubernetes’ view of ingest health. The alternative is to template them into the chart, with the dashboard copied into it.
11SPEC §12 also asks for multi-arch images pushed to GHCR on main, and no milestone has taken that on yet. Does it belong in M8?No. Nothing in M8 needs a public image, and an arm64 build doubles the build time. I suggest doing it after M8, together with M9’s README walkthrough, so that walkthrough can helm install from GHCR.

Heads-up: not in M8

  • The operator doesn’t check mappings at admission. A broken mapping is still accepted by kubectl apply, and only the status reports it. Rejecting it at admission needs a validating webhook, and that webhook needs TLS certificates.
  • Uninstalling: delete the CustomerIntegrations before the operator, or their finalizers keep them around. make down deletes whole clusters, so it isn’t affected.
  • ingest-cli has no image. To replay dead letters in k3d, run kubectl port-forward svc/nats 4222 and use ingest-cli locally, with the mappings from customers/.
  • Compose has no operator. make up keeps running the all-in-one ingest.
  • Your M7 clusters need one make down before the first make k8s of M8.
  • The e2e job builds five release images, so expect it to take 15 to 20 minutes.
