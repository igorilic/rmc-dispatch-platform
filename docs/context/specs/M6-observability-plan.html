Milestone 6 plan: observability

November 10, 2026

Today, ingest and dispatch only write log lines. The compose stack already runs Prometheus, Grafana and Jaeger, but nothing sends them data. Milestone 6 connects all three. An order’s trace starts when ingest receives it, crosses NATS in a message header, and ends at the re-dispatch that planned it, with the new version and the size of its diff on the span. Both services export the Prometheus metrics that SPEC §8 lists, and Grafana opens on a provisioned “Dispatch overview” dashboard.

Done when:

  • In make up, Jaeger shows one trace per order delivery. It runs from the webhook or SFTP file, through ingest’s publish, NATS and dispatch’s order intake, to the re-dispatch that planned the order. A truck reporting out_of_service over MQTT produces the same kind of trace.
  • Prometheus scrapes ingest and dispatch. Four of SPEC §8’s five metrics exist: ingest throughput per customer, DLQ size, re-dispatch latency and the pour-gap distribution. Edge sync lag arrives with the plant-agent in M7.
  • Grafana opens on “Dispatch overview”, and after make demo every panel shows data.
  • make demo ends by printing a Jaeger link to its first order’s trace, and the dashboard’s URL.
  • An integration test proves that a trace crosses NATS into the re-dispatch. Another test proves that the dashboard queries only metrics the services export.
  • make test, make audit and CI are green, and make up is healthy.

Where telemetry flows

One trace, end to end

Every span is a tracing span. A tracing-opentelemetry layer exports them to Jaeger, next to the console logs we already have. The trace crosses three boundaries:

  1. Ingest to NATS. Bus::publish runs inside a publish span and writes that span’s W3C traceparent into the message headers, next to Nats-Msg-Id. Webhooks, SFTP, MQTT and ingest-cli replay all publish through it, so all of them get the header.
  2. NATS to dispatch. The intake reads the header and makes its apply event span a child of the publish span. A message without the header, such as one published before M6, starts a new trace.
  3. Intake to the worker. Each trigger carries the span it was sent from. The redispatch span is a child of its first trigger’s span. Triggers merged into the same run become links on that span (decision 3).

Spans carry ids and counts, never payloads. Raw records stay in the DLQ, where they already are. Two rules keep Jaeger readable:

  • Only our own crates’ spans are exported, at info and above. Library internals (NATS, sqlx, hyper, and the exporter’s own HTTP calls) are left out. RUST_LOG still controls the console as before.
  • GPS and drum messages aren’t traced (decision 4). They make up about 99% of the messages, at roughly two per second, and never trigger a re-dispatch.

The “Dispatch overview” dashboard

The dashboard is provisioned from deploy/grafana/, the place SPEC §10 gives it, and is Grafana’s home page. It has four rows:

  1. Current plan. Stat tiles for the version, planned and unplanned orders, gaps over the limit, the maximum gap and empty km.
  2. Pour gaps. A bar chart of the current plan’s gap buckets.
  3. Re-dispatch. Runs per minute by outcome, latency at p50, p95 and p99, and triggers per minute by kind.
  4. Ingest. Records per second by customer, stacked by outcome, and DLQ size by integration.

Its header links to Jaeger and to the Swagger UI.

Steps

Each step ends green and becomes its own commit.

Step 1

The telemetry crate. First, check rust-toolchain.toml, the crate versions and the pinned Prometheus, Grafana and Jaeger images. Then build:

  • init(service), which sets up console logs as today, the OTLP span exporter with the target filter, and the metrics listener, and returns a guard that flushes spans at shutdown;
  • inject and extract, which move a span’s context into and out of a NATS HeaderMap;
  • the sampler that drops GPS and drum roots, and follows the parent’s decision everywhere else.

Unit tests check that a context round-trips through headers, that a GPS root isn’t sampled while a ticket root is, and that a child of an unsampled remote parent isn’t sampled either. The ingest and dispatch binaries switch to init, and compose gets the endpoint variable.

Step 2

The trace across NATS. This step adds the ingest spans and the header, the intake span, triggers that carry their span, the redispatch span with its children and links, and the API spans. Tests, with an in-memory span exporter:

  • in ingest/tests/bus.rs, an event published inside a span carries that span’s traceparent in the stored message;
  • in dispatch/tests/intake.rs, against real NATS and Postgres, an order published through ingest’s Bus produces publish, apply-event and redispatch spans with one trace id, each the parent of the next;
  • in the same file, two triggers merged into one run give one redispatch span, with a parent from the first trigger and a link to the second;
  • a webhook router test checks that the 202 response carries the trace id (decision 9).

Step 3

Metrics. This step adds ingest’s record counter and DLQ poller, and dispatch’s latency histogram, trigger counter and plan gauges. The gap buckets are a pure function, with unit tests for gaps that fall on a boundary, a single-load order and frozen loads. The other recording calls are one line each and get no tests of their own. Step 4 checks them end to end.

Step 4

Prometheus, Grafana and the dashboard. This step adds:

  • the scrape config;
  • Grafana provisioning, with the dashboard as the home page and anonymous read-only access (decision 8);
  • healthchecks for Prometheus and Grafana, so make up --wait covers them. Jaeger gets one too if its image has a tool to run it with.

A test in dispatch/tests, which can already see ingest, reads dispatch-overview.json and fails if a query names a pourline_ metric that neither service defines.

Step 5

Demo, README, and a full run.

  • make demo prints a Jaeger link to its first order’s trace, using the trace id from the webhook response, and the dashboard’s URL.
  • The README gets an “Observability” section with what to open, the trace’s path, the metrics table and the updated Grafana access.
  • Run make demo on a fresh stack. Then confirm in Jaeger that the order’s trace reaches its redispatch span, and confirm through Prometheus’s API that every dashboard query returns data. Commit.

Decisions I need from you

I’ll use the default unless you say otherwise.

#QuestionMy default
1Which metrics stack?metrics with metrics-exporter-prometheus, which Prometheus scrapes. SPEC §11 names it, it’s Prometheus’s native model, and metric names reach Prometheus exactly as written. The alternative is OpenTelemetry metrics pushed over OTLP to Prometheus’s OTLP receiver. That would mean one SDK for both signals, but metric names get translated, and the push needs a second exporter endpoint.
2Does ingest honour a traceparent that a customer sends?No. Every delivery starts a new trace. Customers are untrusted callers, and their trace ids mean nothing in our Jaeger.
3Which trace does a re-dispatch of merged triggers belong to?Its first trigger’s trace, as a child. Every other trigger in the run becomes a link, which Jaeger shows as a reference from the redispatch span. The other traces end at their intake span, and the link leads on from there.
4Do we trace GPS and drum messages?No. At about two per second they would bury the order traces in search results, and they would push the order traces out of Jaeger’s in-memory store first. They are still counted in pourline_ingest_records_total. Status reports and batch tickets are traced, because they freeze loads or trigger a re-dispatch.
5What does “pour-gap distribution” measure?The current plan: one gauge per gap bucket, replaced on every new version. The alternative is a histogram over every stored version’s gaps. That counts an unchanged pour again with every version, so busy periods would look worse than they are.
6Where does “re-dispatch latency” start?When the worker takes the batch, and it ends when the version is stored. Waiting in the queue shows up in the trace as the gap between the intake span and the redispatch span. A queue-wait metric can follow if the queue ever backs up.
7Edge sync lag?M7, together with its dashboard panel. Until the plant-agent exists, there is nothing to measure.
8How do you get into Grafana?Anonymous read-only access, with “Dispatch overview” as the home page, so the link from make demo opens without a login. admin / admin stays for editing. The port binds to 127.0.0.1, like every other port.
9Does the webhook’s 202 response carry the trace id?Yes, as a new trace_id field next to the counts. Support can then find a customer’s delivery in Jaeger, and the demo can link to its trace directly. The change only adds a field, so existing clients aren’t affected.

Heads-up: not in M6

  • Log lines don’t carry trace ids. That only pays off with a log backend, such as Loki, which SPEC doesn’t ask for.
  • There are no exemplars that link histogram buckets to traces, because the Prometheus exporter doesn’t support them, and there are no alerting rules.
  • Dead letters don’t keep their trace context. A replay starts a new trace.
  • Jaeger keeps traces in memory, so make down or a restart loses them. That’s fine for a local stack.
